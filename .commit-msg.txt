feat: add slash commands and a CLI delete, sharing one delete core

Deletion was previously reachable only by the model through a tool. Users
now have two direct routes, and both write the same safe zone:

- /safe-delete <path>      move into the safe zone (--preview to look first)
- /safe-delete list        what is recoverable
- /safe-delete restore <id>  put it back
- /safe-delete clean       prune now (--dry-run to look first)
- /safe-delete config      every setting with its current value, what it
                           does, what changing it does, and its valid range
- /safe-delete config <key> <value>   change one setting
- dsh-safe-delete delete <path> [--preview]  from a terminal

The slash commands and the plugin-page form read and write through the same
host settings service, so a change made in either place shows up in the
other after a restart. There is no second copy to reconcile.

delete-core.ts is extracted so the tool, the command and the CLI cannot
drift apart on who needs approval, how thresholds are computed, or what
counts as off-limits. The CLI refuses anything that needs interactive
approval instead of silently allowing it: a terminal has no approval
channel, and pretending otherwise would be the exact failure this plugin
exists to prevent.

Two defects found while testing:

- the command parser split on the first word, so `/safe-delete C:\Work\x`
  was read as the subcommand "c:\work\x" and refused. It now only treats
  the first word as a subcommand when that word is a known one.
- `restore` appeared in the help text and the subcommand list but had no
  handler, so it was treated as a path and would have tried to delete a
  file named after the id.
