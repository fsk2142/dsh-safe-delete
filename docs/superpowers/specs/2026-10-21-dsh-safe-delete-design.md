# dsh-safe-delete 设计

日期：2026-10-21

## 它为什么存在

在 DSH 里，删除是一条**不可逆的单行道**：一条命令执行完，数据就没了，中间没有任何可以后悔的状态。深层的问题不是"模型不听话"，而是这条路径缺少一个可回退的中间态。

dsh-safe-delete 要做的事只有一件：**把删除从不可逆变成可逆**。它不试图让模型更听话，而是让"删错了"这件事不再致命。

## 它替换谁

替换 `@suagr_xl/dsh-safety`。两者不并存：同一条命令被两套闸门拦，会互相打架。

保留 dsh-safety 里被证明有效的思路（拦车闸 + 唯一删除通道 + 审计），丢掉与删除无关的部分（组合快照、重启前体检、编码校验、符号链接逃逸分析）。

关于被替换的那个插件，有一处事实需要澄清：**当时它并未安装**。因此没有证据表明它存在具体盲区，也**不应**把"补齐它的漏洞"当作设计目标。目标是按第一性原理，让删除在 DSH 里可逆。

## 为什么要换掉它

dsh-safety 的审批必须离开 DSH 界面、另开终端敲 `dsh-safety allow <id>`。审批发生在被保护的系统之外，这是体验上的根本缺陷：一个"保护"机制要求你先绕过它所在的界面才能使用。

根因（已核实）：

- dsh-safety 用的是 `ctx.tools.guard()`。这是一个**单调守卫**——只能返回拒绝理由，没有回话通道。它拦下调用之后，模型只能等一个外部 CLI 动作。
- DSH 自带 `@deepseek-ai/dsh-user-approval`（宿主侧审批 seam）+ `@deepseek-ai/dsh-client-ui-approval`（聊天框上方的审批卡片，"允许一次 / 拒绝"，回车与 Esc 绑定快捷键）。这套东西本来就是**当面点一下**的通道，dsh-safety 完全没接。
- 接入点是 `tools/pre-execute` 瀑布：它的返回值除了 `allow` / `deny` 还有 `ask`，`ask` 会经由 `ApprovalService.request()` 走到上面那张卡片，`allowed-once` 才放行。
- **前提**：审批策略必须是 `ask`。策略为 `never` 时（例如 `danger-full-access` 权限预设），`never` 在 `decide()` 里于瀑布分发之前直接返回 `rejected`，卡片根本不会出现。插件对此的应对见下文「`never` 策略下的降级」。

## 目标

1. 任何删除都不能直接落到数据上：目录树删除只能进安全区，不允许裸 shell 执行。
2. 授权发生在 DSH 界面里，不需要另开终端。
3. 删掉的东西在保留期内可原样取回。
4. 一次删除发生前，能看清"删什么、多大、几个文件"。

## 非目标

- 不做组合快照 / 重启前体检 / 编码校验（dsh-safety 的其余职能，不在本插件范围）。
- 不做防恶意插件（进程内同权，拦不住）。
- 不做"永久删除"的隐藏后门：清理是唯一销毁路径，且必须可配置、可关闭。
- 不接管 DSH 自身沙箱与审批策略，只使用它们。

## 设计决定

| 决定 | 内容 |
|---|---|
| 定位 | 直接替换 dsh-safety，不并存 |
| 授权通道 | 界面内点击授权；CLI 作为兜底保留 |
| 安全区保留 | **7 天 + 容量上限 + 手动清理**，三层叠加 |
| 弹卡范围 | **只有危险路径弹卡**；普通工作区文件直接进安全区，不打断 |
| 容量上限 | **20 GB**，超出时最旧优先清理 |

### `never` 策略下的降级

审批策略是 `never` 时不返回 `ask`（因为只会被静默驳回，结果等于"什么都不许删"），而是降级为直接走安全删除：文件仍进安全区、仍可恢复，只是少了当面确认。

代价必须写明：危险路径（家目录、profile 清单、`node_modules`）的删除失去一次人工确认，只剩"可恢复"这一层。想两层都要，就把权限预设换成使用 `approval: ask` 的那个。

## 核心概念：安全区（不是回收站）

删除的内容**不直接进回收站**，而是进一个安全区，等保留期结束后统一移除。

- **移动而非复制**：同一卷内 `rename`，瞬间完成，不占额外空间、不产生 IO 峰值。跨卷（安全区与目标不在同一盘）时默认拒绝；只有显式开启 `crossVolumeCopy` 才退化为"复制 + 登记 + 删源"，并在卡片上明说这一步会发生。
- **保留期**：每条记录带 `expiresAt = 移入时间 + 7 天`。
- **容量上限**：安全区总占用超过阈值时，按"最旧优先"淘汰，直到回落到阈值以下。
- **手动清理**：可随时清空或清除指定条目。
- **清理是唯一销毁路径**：只有清理会真正从硬盘抹除。除此之外任何代码路径都不许删除用户数据。


## 分层防线

```
模型发起删除
   │
   ├─ ① 拦车闸（tools/pre-execute 瀑布）
   │    bash / pwsh / run_code / terminal_send 里的破坏性命令
   │    → 判定：这不是安全删除 → deny + 指路
   │
   └─ ② 安全删除工具（safe_delete）
        唯一会动用户数据的删除入口
           → 预览 / 分类 / 命中保护路径
           → 需要授权时返回 ask → 界面卡片 → allowed-once
           → 移入安全区
```

**只有两道，不是三道。** 关于纵深防御的一个重要核实结果：DSH 内核**没有** `fs/delete-intent` 事件。核实方式为在 asar 全量扫描 16,726 个文件，命中数为 0；`@deepseek-ai/dsh-fs` 只定义 `fs/write-intent`、`fs/edit-intent`、`fs/observed` 三类意图事件，且只由 `write` / `edit` 触发。dsh-safety 里监听 `fs/delete-intent` 的那段代码监听的是一个永不触发的事件，属于死代码——不能作为防线计入。

这意味着一个必须诚实面对的事实：**删除只有一条到达硬盘的实路，就是 shell**。DSH 内核没有 `delete_file` / `remove_file` 这类工具（已枚举全部核心工具名确认）。所以拦车闸覆盖 `bash` / `pwsh` / `run_code` / `terminal_send` 这四个入口，就是完整的覆盖面，不存在"漏掉某个 fs 删除工具"的缺口。同理，`fs/write-intent` 只能防改写、防不了删除，本插件不依赖它。

### ① 拦车闸的识别对象

已核实需要覆盖的工具名：`bash`、`pwsh`（persistent 版同名）、`run_code`、`terminal_send`（可把命令送进已开的终端会话）。

识别的破坏性模式（Windows 与 POSIX 双语）：

- 递归删除：`Remove-Item -Recurse`、`rm -r/-rf/-fr`、`rd /s`、`rmdir /s`、`del /s`、`shutil.rmtree`、`fs.rm` 带 `recursive`。
- 非递归删除：`Remove-Item`、`del`、`erase`、`rm`、`unlink`、`fs.unlink`。
- 变量与拼接：`$env:X\...`、`%X%\...`、`${X}/...`、`$HOME`、`~` 展开后是否落到保护路径或工作区根。
- 通配符放大：`Remove-Item *`、`rm -rf ./*`、`del *.*`。

判定结果三选一：

- **放行**：目标是明确的临时文件、构建产物，且用户已显式要求（配置项 `allowPatterns`，默认空）。
- **指路**：删除意图明确 → `deny`，理由里给出"用 `safe_delete`"这条正路，并提示可预览。
- **升级**：无法判定目标（变量、管道、动态拼接）→ `ask`，让用户在卡片上看到原始命令再决定。

### ② 安全删除工具

参数：

| 参数 | 作用 |
|---|---|
| `path` | 绝对路径 |
| `preview` | 只描述不动手：大小、条目数、顶层预览、是否跨卷、分类结论 |
| `reason` | 为什么要删（写进审计与卡片） |

行为：

1. `preview:true` → 返回描述，不动任何东西。
2. 路径分类：`free`（普通工作区）/ `confirm`（用户主目录、插件源码、预设）/ `protected`（profile 清单、补丁层、lockfile、`node_modules`、DSH 安装目录）。
3. **`confirm` / `protected` 才需要授权**（权衡见下）。`free` 路径直接移入安全区，不打断。**模型无法自批**：`force:true` 这类模型可自设的标志不作为授权依据。
4. 移入安全区，写审计，返回取回方式。

**为什么 `free` 路径不弹卡**：安全区本身就是最有效的保护——进了安全区的文件 7 天内都能拿回来，弹卡是多余的打断。弹卡的价值在于那些"进了安全区也不该轻易动"的东西：用户主目录、插件源码、profile 清单、`node_modules`。这个分层让日常干活不被打断，同时危险动作仍然当面确认。

### ③（已删除）fs/delete-intent 兜底

原设计假设存在 `fs/delete-intent` 瀑布可作第三道防线。**核实后发现该事件在 DSH 内核中不存在**，全量扫描命中 0，dsh-safety 的同名监听从未被触发。该层取消，不影响覆盖面——内核没有删除类文件工具，删除只经 shell 到达硬盘。

## 授权流程（用户可见部分）

```
模型想删 C:\Work\proj\build
  → 卡片出现：工具 safe_delete 请求执行
     "删除 C:\Work\proj\build —— 目录，1,284 个文件，共 2.3 GB，
      移入安全区后 7 天内可恢复"
     [拒绝]  [允许一次]
  → 回车 = 允许一次，Esc = 拒绝
  → 允许后：移入安全区，返回条目 id
```

关键性质：

- **一次性**：`allowed-once` 只对这一次调用有效，不复用、不记忆。
- **界面内**：不需要离开 DSH，不需要另开终端。
- **带因果**：卡片上显示的是系统按真实路径判定出的后果，模型的自我陈述不能替代它。
- **可拒绝且模型能分辨**：`rejected`（人说不）与 `unavailable`（没有通道）对模型是两条不同的信息，前者不许重试，后者要报告给用户。

`never` 策略下：`ask` 一律变成拒绝，本插件的删除能力随之不可用（只剩拦车闸）。这是刻意的 fail-closed：**没有审批通道，就不许删。**

## 安全区布局与取回

```
$DSH_HOME/.dsh-safe-delete/
  items/<id>/            移入的原始内容
  index.json             每条：原始绝对路径、移入时间、到期时间、大小、条目数、跨卷标记、原因
  journal.jsonl          审计：移入 / 取回 / 清理 / 拦截 / 授权
```

取回：按 `id` 还原到原始路径；原路径已被占用时，还原为 `.restored-<时间戳>` 同级兄弟，绝不覆盖。

重启安全：全部状态落盘，DSH 重启后安全区与到期时间照旧。

## 清理策略（三层叠加）

| 层 | 触发 | 动作 |
|---|---|---|
| 时间 | 条目 `expiresAt` 到期 | 该条目销毁 |
| 容量 | 安全区总占用 > `maxBytes` | 最旧优先销毁，直到回落到阈值下 |
| 手动 | 用户主动 | 清空 / 清除指定 id |

清理时机：执行安全删除时顺带检查、以及一个低频定时器。**不做后台常驻扫描**——安全区不该有自己的生命。

清理前 `dryRun` 可选：列出"下一次清理会销毁什么"，让用户先看一眼。

## 配置项（初版）

| 键 | 默认 | 含义 |
|---|---|---|
| `retentionDays` | `7` | 保留天数 |
| `maxBytes` | `20 GB`（`21474836480`） | 安全区容量上限 |
| `stateDir` | `<DSH_HOME>/.dsh-safe-delete` | 状态目录 |
| `blockShellDeletes` | `true` | 拦车闸总开关 |
| `allowPatterns` | `[]` | 显式放行的路径模式（构建产物等） |
| `autoPrune` | `true` | 是否自动按时间/容量清理；关掉后只剩手动 |
| `crossVolumeCopy` | `false` | 跨卷时是否允许复制式移入（关掉则拒绝并说明） |

## 与 DSH 内置能力的关系

| 内置 | 关系 |
|---|---|
| `dsh-user-approval` | 本插件的授权**就是**走它，不另造通道 |
| `dsh-client-ui-approval` | 卡片由它渲染，本插件不写 UI |
| `dsh-permission-presets` | 预设决定审批策略；`never` 下本插件删除能力自动失效 |
| `dsh-sandbox-policy` | 第一道隔离，比本插件更强；本插件是删除专用补充 |

## 技术约束（已核实）

- 零外部 import：只依赖 Node 内置。bundles 以 `link:` 裸装时没有自带 `node_modules`，import `@deepseek-ai/*` 会在启动时解析失败。
- 工具定义手写 JSON Schema 子集，不使用 `defineTool`。
- **fail-soft**：注册失败只降级记日志，安全插件自身绝不能成为 DSH 启动失败的原因。
- 审批请求必须在打开的 turn 内发起（`ApprovalService.request()` 的前置条件），拦截发生在工具调用期，天然满足。
- 会话策略为 `never` 时，`ask` 请求不会到达界面而是直接 `rejected`；拦截逻辑要把这条路径当作"无授权通道"处理。
- **不存在 `fs/delete-intent`**：内核只提供 `fs/write-intent` / `fs/edit-intent` / `fs/observed`，且只由 `write` / `edit` 触发。本插件不得假设能拦截"某个 fs 删除工具"，因为内核没有这种工具。
- 工具名已核实：`bash`、`pwsh`（持久化版同名）、`run_code`、`terminal_send`；`terminal_open` 只开会话不送命令，无需拦截。

## 风险

| 风险 | 应对 |
|---|---|
| 拦车闸误伤正常命令 | `allowPatterns` 白名单；`preview` 让用户先看；被拦时给的是"改走安全删除"而非死路 |
| 模型绕过（换工具、换编码、拼接路径） | 覆盖全部删除类工具名；变量与拼接无法解析时升级为 `ask` 而非放行；被拦后明确禁止换姿势重试 |
| 跨卷移入变慢/失败 | 默认 `crossVolumeCopy:false`，在预览阶段就说明会失败，让用户改选销毁或换安全区位置 |
| 安全区被误删 | 安全区自身在 `protected` 分类内，`safe_delete` 拒绝删除自身状态目录 |
| 清理误伤 | 清理是唯一销毁路径且可 `autoPrune:false` 全手动；`dryRun` 先看 |

## 成功标准

1. 模型执行 `Remove-Item -Recurse` 时被拦下，理由里指明走 `safe_delete`。
2. 用户全程不离开 DSH 界面即可批准一条删除。
3. 被删的目录树能在 7 天内按 id 原样取回。
4. 安全区超过容量上限时，最旧条目被清理，日志可查。
5. 关闭 `autoPrune` 后，除手动清理外没有任何代码路径销毁数据。

## 待定（实现阶段再定，不影响开工）

- 安全区默认是否与工作区同盘：需要在首次使用时探测并提示。
- 卡片上是否展示文件树预览（受审批 seam 只传 `reason` / `displayReason` 的限制，富信息可能需要放在 `reason` 文本里）。
- 独立 CLI 保留到什么程度：兜底可用即可，还是提供完整管理命令。
