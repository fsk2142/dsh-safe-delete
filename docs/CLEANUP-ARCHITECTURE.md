# 清理架构：后台子进程 + 批量回收

## 为什么改

2026-10-30 的事故：调用插件删除文件后，DSH 所有会话卡在"载入历史…"。

根因链条：

1. `pruneIfDue` 挂在 6 个工具的 `beforeExecute` 上，每次工具调用都执行
2. 节流只有 1 秒，而一次完整清理要为每条调系统回收站（实测 1049 ms/次）
3. 用户安全区有 28,724 条过期条目 → 单次清理约 **8.4 小时**
4. 8.4 小时远大于 1 秒节流 → **每次工具调用都从头再跑一遍**
5. 它在串行队列里、用同步 fs → 事件循环被占住 → 会话加载停摆

## 现在的架构

```
DSH 主进程
  ├── 6 个工具（只处理本次操作，不等清理）
  ├── pruneIfDue      → 判断是否到期，投递请求（约 9 ms 返回）
  ├── afterMove       → 投递请求
  ├── 斜杠 clean      → 投递请求，返回任务 id
  └── 面板清理        → 投递请求
        │
        │ spawn（非 execFileSync —— 后者会阻塞事件循环）
        ▼
  独立子进程 cleanup-worker
    ├── 恢复上次残留批次（见下）
    ├── 每批最多 500 条 / 256 MiB
    ├── 写 manifest → 逐条同卷 rename 聚合成一个目录
    ├── 对这**一个目录**调一次系统回收站
    └── 从索引移除这批 id
```

## 三个关键设计

### 1. 搭车触发，不搭车执行

工具调用只**投递**清理请求，不等待结果。`spawn` 是 fork+exec，9 ms 返回；
即使子进程要跑几小时，这次工具调用也早已返回。

**不能用 `setImmediate` 或 `void promise()` 代替**：那些仍在同一个事件循环里
跑同步 fs 与 `execFileSync`，看起来是"后台"，实际照样卡住宿主。

### 2. 批量回收（实测 47 倍）

回收站是**按目录树**工作的。把 N 条先 rename 进同一个目录（同卷，0.56 ms/个），
再对那个目录调一次：

| 方式 | 50 条 | 28,724 条 |
|---|---|---|
| 逐条调回收站 | 52 秒 | 8.4 小时 |
| 聚合后一次 | **1.1 秒** | **约 17 秒** |

实际按每批 500 条切分（故障隔离），28,724 条约 58 次调用。

### 3. 崩溃可恢复

聚合到一半被杀是最危险的窗口：内容已搬出 `items/`，索引仍指向它。

**做法**：在第一次 rename **之前**写 `batches/<id>/manifest.json`，列出本批
全部预期 id。恢复时按每个 id 在两处找：

| 内容在哪 | 处理 |
|---|---|
| `items/<id>` | 没搬走，不动 |
| `batches/<id>/items/<id>` | **搬回 `items/`** |
| 两处都没有 | 从索引移除（内容真没了） |

选"搬回去"而不是"接着回收"：崩溃说明环境当时有问题，把用户内容原样还回去
比替用户继续删除更安全。前者可逆，后者不可逆。

## 目录结构

```
<stateDir>/
  index.json                     活动索引
  items/<entryId>/...            活动条目内容
  journal.jsonl                  审计流水
  cleanup-job.json               最近一次清理任务状态
  cleanup.lock                   单实例锁（含 pid）
  batches/<batchId>/manifest.json  批次清单
  batches/<batchId>/items/<id>/... 聚合中的内容
```

## 锁与单实例

`cleanup.lock` 用 `wx`（独占创建）写入 `{pid, at}`。

接管规则：**过期且 pid 已死**才接管。只看过期会误杀正在慢跑的长任务；
只看 pid 会漏掉崩溃后残留的锁。

## 已知边界

- **聚合回收后，Windows 回收站里是一个批次目录**，不是 500 个独立文件。
  要按单项恢复，需要先恢复整个批次再凭 manifest 查找。
- **回收结果不确定时保留数据**：`Shell.Application` 的 `InvokeVerb('delete')`
  不是完备事务结果。当前用"原路径消失"判定成功，这在真实 Windows 环境
  （网络卷、回收站禁用、确认对话框）下可能需要更严格的 API（`IFileOperation`）。
- **跨卷**：聚合要求安全区与 `batches/` 同卷。跨卷会失败并被保守跳过。

## 验证

```bash
pnpm typecheck && pnpm vitest run && pnpm build
node scripts/zz-e2e-lib.mjs   # 用真实产物跑一次子进程（可选，需手工建）
```

单元测试无法覆盖"打包后 worker 入口还在不在"这类问题——必须真跑一次产物。
两次踩坑都属于这一类：`__dirname` 在 ESM 下不存在、`import.meta.dirname`
被打包器改写成 `__dirname`。最终用 `fileURLToPath(import.meta.url)`。
