# 边界与设计取舍（BOUNDARIES）

这份文档回答「插件保证什么、不保证什么、为什么」。操作步骤在
[`README.md`](../README.md)，参数与配置全表在 [`REFERENCE.md`](REFERENCE.md) ——
这里是实现与验证时的依据，不是操作步骤。

---

## 1. 第 2 层的边界（R-01）

「安全区条目到期后移入系统回收站」不是无条件的第 2 次机会。以下是实测确认的边界：

| 情况 | 实际结果 |
|---|---|
| 同卷移动到回收站 | 进回收站，可从资源管理器还原 |
| 跨卷（源在 D、安全区在 C） | 安全区在 C 盘**真实占一份空间**；清理时只还回 C 盘，D 盘那份早已让出 |
| 安全区所在卷的文件系统不支持回收站 | 直接永久删除，**没有第 2 层** |
| 回收站被组策略关闭 | 同上 |
| 超过回收站配额 | 按系统策略处理（通常是永久删除最旧的） |

**能保证的是**：第 1 层（安全区）始终可用，`safe_zone_restore` 一定能把内容取回，
直到保留期结束。

**不能保证的是**：第 2 层一定存在。依赖它做"最终保险"是不可靠的 ——
保留期内的安全区才是可靠的那一层。

## 2. 谁会让「删除」绕过回收站：两个开关

| 开关 | 范围 | 位置 |
|---|---|---|
| `NoRecycleFiles` | 全局 | `HKCU\...\Explorer\Policies\Explorer` |
| `NukeOnDelete` | **每卷** | `HKCU\...\Explorer\BitBucket\Volume\{GUID}` |

只看全局那一条会漏掉「全局正常、只有某个卷被设成清空」的配置 ——
而那正是想彻底删干净的人会设的。任一卷 `NukeOnDelete=1` 就判为「删除即永久」，
走同一套审批。

判定三态：

| 事实 | 状态 |
|---|---|
| 任一卷 `NukeOnDelete = 1`，或 `NoRecycleFiles = 1` | risky（走审批） |
| 全部卷读到且为 0 | safe |
| 列不出卷 / 某卷读不到 / 值解析不了 | unknown（同样走审批） |

「任一卷为 1 就 risky」是刻意的保守：钩子层拿不到可靠的「目标 → 卷」映射，
所以按最坏情况问人。误报的代价是多一次点击，漏报的代价是不可恢复的数据丢失。

### 「移进回收站」这句话的准确含义

它是**原路径消失**的观测结果，不是「已确认可从回收站还原」—— 插件不读回收站的
`$I/$R` 条目。系统策略、配额、文件系统都会影响可恢复性（见第 1 节）。

## 3. 2.0 的破坏性变更：清理锁不再自动接管

**这是 2.0 唯一的破坏性行为变更，升级后请注意。**

以前，清理进行中若进程崩溃，锁会留在磁盘上；下次清理会因为"持有者已死"而
自动接管那把锁。1.11 之前一直是这么做的。

现在**不再自动接管**。原因是接管协议无法保证互斥——两轮审查各找出一个反例，
最后用真实时序证明：

```
B: 读到陈旧锁，判定可接管
A: 接管成功，建了活锁，开始工作
B: rename(lockPath, tombstoneB)   ← 搬走的是 A 的活锁
B: token 不符 → 退出，但锁路径已经空了
C: write(wx) 成功 → C 也进入工作体
→ A 从未被停止；A 和 C 同时改索引
```

事后比对 token 只能让 B 退出，不能让 A 恢复所有权。真正的修复需要 OS 级锁句柄
（`fcntl` / `LockFileEx`），与本插件的零运行时依赖冲突。

**实际影响**：如果清理进程崩溃，后续清理会**明确失败**并告诉你锁文件的路径。
手动删除那个文件即可恢复：

```
# 默认位置
%USERPROFILE%\.dsh\.dsh-safe-delete\cleanup.lock
```

失败信息里会写出完整路径，直接照做即可。代价是可能需要人工介入一次；收益是
索引不会被两个进程同时写坏。

## 4. 保护范围到哪为止（R-02）

本插件只保护**经过 DSH 工具调用**的删除 —— 也就是 `safe_delete` 工具、
`/safe-delete` 斜杠命令、以及 `bash` 类工具里能被静态识别的删除命令。

| 场景 | 是否受保护 |
|---|---|
| `safe_delete` 工具 | 是 |
| `/safe-delete` 斜杠命令 | 是 |
| 宿主的 `bash` 工具里 `rm` / `del` / `find -delete` 等 | 是（静态识别） |
| 其他插件内部的 `fs.rm` / `fs.unlink` | **否** |
| 你在资源管理器里直接删除 | **否** |
| 编辑器 / IDE 的删除 | **否** |
| `git clean -fdx` | **否** |
| 经混淆的脚本（`powershell -EncodedCommand`） | 拦下并要求人工确认，但**无法解析内容** |

后几类不走本插件的工具管线，因此看不到也拦不住。这是架构边界，不是疏漏 ——
要覆盖它们需要在文件系统层面做拦截（类似文件系统过滤驱动），超出插件能力。

**实际含义**：不要把本插件当成"整个系统的删除保险"。它的承诺是
"**DSH 让我删的东西，都可以反悔**"。

## 5. 「证明只读」的边界（2026-11-05 收紧）

拦截器只放行**能正向证明只读**的命令。以下曾经在放行清单里，现在**要审批**，
因为它们的实际操作由项目自定义：

| 命令 | 为什么不再算只读 |
|---|---|
| `pnpm build` / `npm build` / `yarn build` | 执行 `package.json` 的 `scripts.build`；脚本可以是 `node scripts/cleanup-build.js` |
| `pnpm start` / `test` / `typecheck` / `lint` | 同上，都是项目自定义脚本的入口 |
| `pnpm version`（不带横线） | 改 `package.json` 并打 tag |
| `git pull` | 上游删除已跟踪文件时，工作区里那份会**一并消失** |

仍然放行的只读查询：`git status` / `log` / `diff` / `show` / `ls-files`、
`npm list`、`pnpm ls` / `why` / `outdated`、`pnpm --version` 等。

代价是每次跑构建多一次确认 —— 这是明示的取舍：**「照惯例猜它不删东西」不能写进
「已证明只读」的清单**，而审批疲劳的解法是让放行清单只装真正可证明的项，
不是让它装更多。

## 6. 回收站模式的配额判定（2026-11-08）

Windows 回收站有每卷容量上限。条目**超过上限时会被系统永久删除**，插件无法阻止。

| 判定 | 依据 | 处置 |
|---|---|---|
| 超限 | 大小（或下界）已超过上限 | 删除前弹窗 |
| 未超 | **完整**大小确认低于上限 | 静默进回收站 |
| **无法确认** | 读不到注册表 / 目录枚举没走完 | 按风险处理：弹窗；`never` 下拒绝 |

目录只量顶层是刻意的（递归统计正是回收站模式要省掉的开销），所以目录的大小只是
一个**下界**。下界已超 → 确定超限；下界没超 → 无法确认。

「无法确认」不会一直是死路：`never` 策略下钩子会补一次**有界早退枚举**，
累计一旦超过上限就停，走完都没超就是确定「未超」。代价只落在确实小于上限的
目录上，而那正是删除本来就要遍历的树。

**模式形态**（`root` + `match`）例外 —— 它连目标清单都没有，有界枚举无从下手，
仍在 `never` 下直接拒绝。
